# Value Continuity

> **Upside は伝播可能にする。Downside は伝播させない。**

Status: v0.1（公開初版） · License: [MIT](LICENSE)

**English summary** — Value Continuity is a principle for checking, before implementation, whether a plan, investment, improvement or system keeps generating value through change and failure. It is defined as *keeping the ability to create the next value, even as work, people, technology and products change or fail*. Its central principle, the **Value Asymmetry Principle**, is: *make upside propagable; do not let downside propagate.* It is independent of any specific method; [VCDesign](https://github.com/VCDesign-org/vcdesign) implements it on the side of judgment and responsibility. The documents are written in Japanese.

## Purpose

この文書は、企画・投資・業務改善・システム化において、  
**価値を生み続けられる構造になっているか**を確認するための上位原則を定める。

特定のシステム設計手法、開発手法、組織論には依存しない。

この文書が扱うのは「どう実装するか」ではなく、実装に入る前に確認すべき次の問いである。

> **この取り組みは、良い結果を次の価値へつなげながら、悪い結果の連鎖を止められるか。**

人間による企画判断だけでなく、AIによる企画レビューの判定軸として利用できることを意図する。

## 1. Value Continuity

**Value Continuity（価値の継続）**とは、現在の価値をそのまま保存することではない。

> **変化や失敗があっても、次の価値を生み出せる状態を継続すること。**

現在の業務、担当者、技術、製品が変わっても、次の価値生成に使えるものが残るなら、価値は継続している。

逆に、現在の仕組みが安定していても、それが次の価値を生む能力を失っているなら、Value Continuityは成立していない。

---

## 2. Value Asymmetry Principle

Value Continuityの中心原則を **Value Asymmetry Principle** と呼ぶ。

> **Upside は伝播可能にする。Downside は伝播させない。**

良い結果と悪い結果を同じように扱わない。

- 良い結果は、再利用・接続・学習によって次の価値へつながる道を開く。
- 悪い結果は、境界・上限・復旧によって、それ以上広がらないようにする。

価値の継続には、この非対称が必要である。

上だけを開けば、一度の失敗が全体へ広がる。  
下だけを閉じれば、何も試せず、次の価値も生まれない。

**下を閉じる能力は、上に賭け続けるための原資である。**

### Δ（期待との差）

**Δ** とは、取り組みの開始時に宣言した期待と、実際に起きたこととの差である。
ここでいう期待は、前提としていた条件と、生み出そうとしていた価値の両方を含む。

- 期待を下回る方向の差を **Negative Δ** と呼ぶ。伝播させない。
- 期待を上回る方向の差を **Positive Δ** と呼ぶ。伝播可能にする。

Δ を一律に異常として扱わないことが、Value Asymmetry Principle を判断の場で実践する最初の一歩である。

---

## 3. 5つの原則

Value Asymmetry Principle は、次の5つの原則として実践される。

1. **残す** — 業務・担当・技術が変わっても残るものを、先に決める。  
   標準、判断根拠、データ、接続、技能。保有し続ける人のいないものは残らない。
2. **見つける** — 平均的な改善量ではなく、再利用によって大きく広がる兆候を見る。  
   二回目が安くなる。頼んでいない所から引き合いが来る。別の判断の材料になる。接続するほど一件あたりの価値が上がる。
3. **閉じる** — 悪い広がりは予測せず、境界で止める。  
   損失の上限を先に決め、失敗を局所化し、前提を境界で確かめ直し、単一点への依存を避ける。
4. **試す** — 戻せる範囲で変更する。  
   復旧・切替・撤退できる能力が、試せる回数を決める。
5. **伝える** — 結論ではなく、根拠を次の判断へ渡す。  
   受け取った側は、それを自分の文脈で再判断する。

この順番には意味がある。何を残すかを決めていなければ、広がる兆候は見つけられない。悪い広がりを止められなければ、再び試すことはできない。そして伝えた根拠は、次の取り組みで「残す」ものの起点になる。

---

## 4. Upside — 次の価値を生む構造

企画は、成果そのものだけでなく、成果が次の成果を生む構造を持つべきである。

確認する。

- 成果が一回限りで消費されず、再利用できるか。
- 二回目以降の実行コストが下がるか。
- 別の業務、判断、製品、組織から利用できるか。
- 判断根拠、データ、標準、接続、技能などが残るか。
- 新しい用途や選択肢を生むか。
- 成果が利用されるほど、次の価値生成が容易になるか。

判定のための基本的な問いは一つである。

> **業務が変わったら、この取り組みの何が残るか。**

何も残らない改善を否定するものではない。  
ただし、それを継続的な価値生成と混同しない。

---

## 5. Downside — 継続不能を防ぐ構造

失敗をゼロにすることは目的ではない。

重要なのは、失敗が起きても価値生成そのものを継続できることである。

確認する。

- 一度の失敗で失うものに上限があるか。
- 失敗を局所化できるか。
- 元に戻せるか、別の経路へ切り替えられるか。
- 一つの判断や前提の誤りが、そのまま次へ伝播しないか。
- 単一点への過度な依存がないか。
- 継続困難になった場合に縮小・撤退・終了できるか。

Downsideを閉じる目的は、守ることそのものではない。

> **失敗しても、次の試行が可能な状態を残すこと。**

---

## 6. Asymmetry Check

UpsideとDownsideは別々に評価しない。  
同じ接続、同じ自動化、同じ標準化が、両方を増幅することがあるためである。

企画ごとに確認する。

- 良い結果は、必要な範囲まで広げられるか。
- 悪い結果は、必要な境界で止められるか。
- 再利用性を高めたことで、障害や誤判断まで広がりやすくなっていないか。
- 安全性を高めたことで、変更や実験まで困難になっていないか。
- 下を閉じる仕組みが、上に賭ける能力を増やしているか。
- 上に開く仕組みが、Downsideまで無制限に開いていないか。

理想は、すべてを閉じることでも、すべてをつなぐことでもない。

> **価値は越境でき、損失は越境しにくい構造を作る。**

---

## 7. Continuity Check

企画の現在価値ではなく、変化後に残る価値生成能力を確認する。

最低限、次を問う。

### 業務が変わったら何が残るか

業務手順そのものではなく、標準、判断根拠、データ、接続、技能などが残るか。

### 担当者が変わったら何が残るか

知識や判断が特定個人だけに閉じていないか。

### 技術が変わったら何が残るか

技術固有の実装を失っても、価値、データ、判断、契約、インターフェースなどを引き継げるか。

### 製品・システムが終わったら何が残るか

終了によって、蓄積した知識や選択肢まで失われないか。

### 想定外にうまくいったら何を残すか

上振れを単発の成功として消費せず、再利用可能な形で残せるか。

## 8. Decision

レビュー結果は、単なる点数ではなく、次の判断につなげる。

### Proceed

Value Continuityを満たしており、現在の構造・現在の規模で進められる。

### Expand

Upsideの兆候が観測されており、Downsideの上限と復旧能力の範囲で、対象・規模・接続を広げる。
平均的な効果が出ただけでは Expand の根拠にしない。

### Reframe

価値、対象、境界、前提のいずれかを再定義する必要がある。

### Limit

価値はあるがDownsideの伝播範囲が広すぎるため、対象・権限・規模・期間などを限定する。

### Defer

外部条件や判断材料が不足しており、現時点では確定しない。

### Retire

継続しても次の価値生成につながらず、終了する方がValue Continuityに適う。
開始前の取り組みについては、開始しない判断を含む。

## 9. Review Output

この文書を使って企画をレビューする場合、少なくとも次を出力する。

1. **Upside**
   - 何が次の価値へつながるか
   - 何が再利用可能か
   - 上振れの兆候は何か

2. **Downside**
   - 最大損失は何か
   - どこまで伝播するか
   - どこで止められるか
   - 復旧・撤退できるか

3. **Continuity**
   - 業務・人・技術・製品が変わった後に何が残るか

4. **Asymmetry**
   - Upside propagation と Downside containment が両立しているか

5. **Decision**
   - Proceed / Expand / Reframe / Limit / Defer / Retire

必要に応じて各項目を以下で示す。

- `ok`
- `warning`
- `blocking`

判定には必ず根拠を付ける。

## 10. Implementation Boundary

この文書は実装方法を定めない。

Value Continuityは、経営判断、企画、組織設計、システム設計、運用設計など、それぞれの層で異なる方法によって実装される。

個別の方法論は、この原則を満たすための手段であり、Value Continuityそのものではない。

VCDesign（Value Continuity Design）は、そのうち特に **判断と責任** の面からValue Continuityを実装する方法論として位置づける（[VCDesign-org/vcdesign](https://github.com/VCDesign-org/vcdesign) / [vcdesign.org](https://vcdesign.org)）。

方法論は変更されてもよい。  
この文書が定めるのは、その上位にある判定構造である。

## Summary

Value Continuityとは、

> **変化と失敗の中でも、次の価値を生み出せる状態を継続すること。**

そのための中心原則は、

> **Upside は伝播可能にする。Downside は伝播させない。**

である。

企画時に問うべきことは、単に「効果があるか」「安全か」ではない。

> **価値が次の価値を生み、失敗してもその活動を続けられる構造になっているか。**
